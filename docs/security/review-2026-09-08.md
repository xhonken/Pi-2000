# Security Review — 2026-09-08

## Scope and conclusion

Reviewed the Python API, accounts/roles/sessions, private files and quotas, browser and terminal proxies, desktop HTML/JavaScript, systemd/Caddy settings and relevant installed packages. Checks ran locally on the server. Functional attack tests used disposable accounts and a temporary database. Production checks were read-only apart from the documented installations and Chromium restart.

Several concrete issues were fixed and deployed. The tested file and session paths did not expose another account data. This is not a guarantee that no vulnerabilities exist, a complete external penetration test or approval for unknown/malicious tenants. Network isolation and hard resource quotas remain outstanding.

## Resolved findings

1. **Locally accessible web-server administration — high impact if local code runs.** Caddy HTTP administration at `127.0.0.1:2019` was readable by `win2k-admin` (HTTP 200). Browser sandboxes share the host network namespace, making a local TCP endpoint an insufficient boundary. No attempt was made to change Caddy through it. Administration moved to a Unix socket in a mode-0700 directory owned by `caddy`. After installation, TCP returned connection refused and the application account received permission denied on the socket. HTTPS and `systemctl reload caddy` worked. This follows the [Caddy administration guidance](https://caddyserver.com/docs/api).

2. **Revoked permissions during an in-flight request — high impact for administrative changes.** Several handlers used permissions checked before awaiting the JSON body. They now recheck the session, version and role after reading the body and before mutation. This covers accounts, connections, workspace, desktop and file metadata including quotas. Upload and text-save completion already had rechecks. A regression holds a request open, revokes its session and verifies HTTP 401 with unchanged data.

3. **Password attempts and resource use — strengthened.** Rate limiting previously depended only on an address key derived from X-Forwarded-For. Added a normalised account key (20 attempts per five minutes), a global login limit (60/minute), own-password-change limits and at most two simultaneous scrypt calculations. Client cancellation does not free a calculation slot until scrypt completes. Rate-limit keys have expiry, cleanup and a size bound. These limits live in process memory and reset on restart; they do not replace network protection against distributed overload. Deliberate failed attempts can temporarily deny an account login, a remaining availability tradeoff.

4. **Script protection — defence in depth.** The desktop Content Security Policy restricts scripts to local static resources and blocks inline scripts, embedded objects and base-URL changes. Inline styles remain allowed for window positioning and Ace. The policy is in the entry-page meta element; the streaming iframe is a separate document context. An injected inline test script was blocked on the production login page. The editor UI test passed with CSP enabled. This does not establish that the entire system is immune to XSS.

5. **Unbounded connection objects — bounded.** Accounts now have at most 5,000 SSH profiles/folders. Files already had a 5,000-object limit and byte quotas including Recycle Bin contents and upload reservations.

6. **Chromium — updated.** Updated chromium, chromium-common, chromium-sandbox and chromium-l10n from 152.0.7977.75 to the configured Raspberry Pi package `152.0.7977.82-1~deb13u1+rpt1`. Only the project Chromium main process was gracefully ended; its existing supervisor restarted it. The new process used the new executable, not a deleted old binary. The session worker was not restarted. Such browser restarts can reload pages and lose unsaved form values.

## Remaining risks before untrusted accounts

- **Network access:** SSH profiles can target internal hosts and Chromium shares the host network namespace. Users can reach LAN services. SSH still requires remote authentication, but other LAN services may have weaker protection. Untrusted multi-user hosting needs administrator-controlled destinations and network isolation covering DNS, IPv6 and redirects. Blocking one hostname is insufficient. Existing LAN functionality was retained pending that design decision.
- **Browser disk and memory:** File quotas cover My Files, Desktop and Recycle Bin, not Chromium profiles, cache or Downloads. Browser profiles have no hard per-account disk quota. Global low-disk checks act only when space is low. Memory cgroups were disabled in the running kernel, so the watchdog is a soft after-the-fact limit. Filesystem quotas and working hard memory limits should be implemented and verified before untrusted tenants. CPU/process limits and the watchdog reduce, but do not eliminate, overload risk.
- **SSH/RPC and network boundary:** SSH (22) and rpcbind (111) listened on all interfaces. SSH allowed passwords; root required a key. No nftables ruleset was shown. Router forwarding, an external firewall and actual internet reachability were not verified. These OS services were not changed because they may serve uses outside this project. Adopt SSH keys and restricted network access with a verified recovery route to avoid locking out the owner.
- **Recovery and auditability:** Backups are on the same server/disk. Off-device backups and more complete security logging in protected storage remain necessary. No historical incident investigation or assertion that no compromise ever occurred is included.

## Deployment and recovery

`scripts/install-security.sh` validates Caddy, uses the verified backup/deployment path, moves administration to the private socket and checks access. The previous Caddyfile was saved under `/var/backups/win2k-security-C7qpP0AI/Caddyfile`. Future maintenance must retain the Unix socket: restoring an old Caddyfile can reopen TCP administration. `server/Caddyfile` contains the maintained configuration.
